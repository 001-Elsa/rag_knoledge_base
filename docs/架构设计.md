# 架构设计说明

## 整体架构

```
┌──────────┐ HTTP/SSE/WebSocket ┌─────────────┐
│ 浏览器    │ ←───────────────→ │  FastAPI API │──→ DeepSeek API（改写/生成/追问）
│ Vue3+EP  │                    │  (异步)      │──→ 本地 bge 模型（查询向量化）
└──────────┘                    └──────┬───────┘
                 投递任务 / 订阅通知     │        读写
        ┌───────────────────────────────┼────────────────┐
        ▼                               ▼                ▼
  ┌────────────┐                 ┌────────────┐   ┌──────────┐
  │   Redis     │                 │ PostgreSQL │   │  uploads │
  │ 队列+缓存    │                 │ + pgvector │   │ 文件存储 │
  │ +发布订阅    │                 └────────────┘   └──────────┘
  │ +Token白名单 │                       ▲
  └────┬───────┘                        │ 写入切片+向量
       │ 消费任务 / 发布状态              │
  ┌────┴─────────┐    ┌─────────┐       │
  │ Celery Worker │───→│ Flower  │       │
  │ 解析→切片→向量化（本地 bge）  │───────┘
  └──────────────┘    └─────────┘
```

## 两条核心链路

### 1. 文档入库链路（写路径，异步）

```
上传接口(202 立即返回) → Celery 任务 → 解析(PDF带页码) → 切片 → 批量向量化 → 写入 pgvector
                                    └─ 每次状态变化 publish 到 Redis → WebSocket 推给浏览器
```

- **为什么异步**：大 PDF 解析 + 向量化耗时可达分钟级，同步做会阻塞请求、打满连接。上传接口只做「流式落盘 + 建记录 + 投递任务」，毫秒级返回 202。
- **状态机**：`pending → processing → ready / failed`，失败时 `error` 字段存原因，任务自动重试 2 次。
- **实时通知**：状态变化经 Redis 发布订阅推到 WebSocket。选发布订阅而不是 worker 直连 WS，是因为 worker 与 API 是独立进程（甚至可以不同机器），worker 不知道用户连在哪个 API 实例上——发布订阅天然解耦，多实例部署也不用改。
- **幂等**：任务开头先删除该文档旧切片再写入，重跑不会产生重复数据。
- **可靠性**：Celery 配置 `task_acks_late=True`，worker 崩溃时任务回队列不丢。

### 2. 问答链路（读路径，流式）

```
问题 → (多轮时)查询改写 → 查询向量化 → 两路召回(向量+关键词，可限定知识库)
     → RRF 融合 → (可选重排) → 拼 Prompt → DeepSeek 流式生成（SSE：rewrite→sources→delta→done→suggestions）
     → 用量落库(UsageRecord) → 推荐追问
```

- **查询改写**：多轮对话里"那第二条呢"这种问题直接拿去检索必然搜不到。有历史时先用一次小的
  LLM 调用把问题改写成独立完整问题（temperature=0、120 token 上限、失败兜底原问题），改写结果
  通过 `rewrite` 事件推给前端展示，可解释性拉满。
- **推荐追问放在 done 之后**：追问生成又是一次 LLM 调用（约 1-2 秒），如果放在 done 之前，
  用户会看着已经完整的回答干等。先 done（前端解锁输入框），追问事件后到后补渲染。

## 关键设计决策与理由

### 为什么选 pgvector 而不是 Milvus / 独立向量库？

- 业务数据（用户、文档、会话）本来就在 PostgreSQL，向量放同一个库里**少运维一个组件**，还能用外键级联删除保证向量与文档的一致性（删文档自动删向量）；
- 百万级以下向量规模 pgvector + HNSW 索引完全够用；
- 若规模到千万级、需要分布式，再迁移 Milvus，检索层已抽象在 `retriever.py`，切换成本可控。

### 为什么切片大小选 512、重叠 64？

- bge-small-zh 的有效输入长度约 512 token，切太长后半段语义会被稀释；
- 太短（如 128）则单片信息不完整，LLM 拿到的上下文碎片化；
- 64 的重叠保证答案落在切分边界时不会被截断；
- 这些都是配置项（`CHUNK_SIZE` / `CHUNK_OVERLAP`），可以用 `scripts/eval_retrieval.py` 量化对比不同取值。

### 为什么用混合检索 + RRF，而不是纯向量？

- 纯向量检索对**专有名词、型号、编号**不敏感（如"XR-500 的保修期"里的 XR-500）；
- 关键词检索正好互补；
- RRF（Reciprocal Rank Fusion）只用排名不用分数，**不需要调两路权重**就有稳定提升，是工业界常用的免调参融合方法。

### 为什么 Embedding 用本地模型？

- DeepSeek 官方不提供 Embedding API；
- bge-small-zh-v1.5 只有 100MB 左右，CPU 就能跑，中文检索效果好；
- 入库和查询必须用**同一个模型**（否则向量空间不一致），本地部署天然保证这一点；
- 模型懒加载 + 进程内单例（双重检查锁），API 启动不被拖慢。

### 对话历史为什么 PG + Redis 两层？

- PostgreSQL 是**事实来源**（不丢数据），Redis 只是热缓存（拼 Prompt 免查库）；
- Cache-Aside：读时 miss 回源并回填；写时同步追加缓存；
- Redis 挂了自动降级直查数据库，主流程不受影响（所有 Redis 操作都包了异常兜底）。

### SSE 流式接口的坑

- POST 请求不能用浏览器原生 `EventSource`，前端手动用 `fetch` + `ReadableStream` 解析事件流；
- 事件顺序设计为 `sources → delta* → done`，来源先推，用户等待生成时就能看到"参考了哪些文档"；
- 流式响应期间请求级数据库 session 生命周期不可靠，**落库使用独立新建的 session**；
- 反向代理部署时需关闭缓冲（响应头 `X-Accel-Buffering: no`）。

### 双 Token 认证设计

- Access Token 30 分钟、完全无状态（不查库不查 Redis），性能好、水平扩展友好；
- Refresh Token 7 天、jti 存 Redis 白名单（key 自带 TTL），登出=删 key；
- **轮换用 GETDEL**：换新 token 时原子地"取出并删除"旧 jti——旧 Refresh Token 一经使用立即作废，
  即使被窃取也无法二次使用（防重放）；并发场景也不会出现两个请求都换出新 token；
- token 里带 `type` 字段并在校验时检查，防止拿 Refresh Token 冒充 Access Token（类型混淆攻击）；
- 取舍：Access Token 不做黑名单（30 分钟窗口内无法强制下线），换来零查询开销——这是经典
  的安全/性能权衡，面试时能主动讲清楚这一点很加分。

### 安全细节

- 密码 bcrypt 加盐哈希，登录失败不区分"用户不存在/密码错误"（防撞库探测）；
- 越权访问他人资源返回 404 而非 403（不暴露资源存在性）；
- 检索、会话、统计查询全部带 `owner_id` 过滤，用户数据严格隔离；
- 上传做扩展名白名单 + 大小限制（流式计数，超限即断，不会先读完整个文件）；
- 前端 Markdown 渲染前经 DOMPurify 过滤（防存储型 XSS）；
- 聊天/上传接口按 IP 限流（slowapi，可切 Redis 存储做多实例全局限流）。

### 可观测性

- `/metrics` 暴露 Prometheus 指标：HTTP 请求量/耗时直方图 + 检索耗时 + LLM 首字延迟 + 问答计数，
  可直接对接 Prometheus + Grafana；
- 每次问答的 token 用量与延迟落库（UsageRecord），业务侧看板与运维侧指标分开存：
  指标是聚合采样（便宜、看趋势），用量记录是精确到每次请求（可对账、可按用户算成本）；
- 健康检查真实探测 PostgreSQL 与 Redis 连通性，返回 503 供容器编排摘除实例。

## 已知取舍（面试可主动聊）

- **关键词召回用 LIKE 扫描**：数据量大时应换 PostgreSQL 全文检索（zhparser 分词）或 Elasticsearch。
- **Access Token 无黑名单**：30 分钟内无法强制下线，换取无状态零开销（见上）。
- **Embedding 在请求线程池里跑**：并发高时应拆成独立的 embedding 服务（如 TEI）水平扩展。
- **WebSocket 单实例内存连接**：多实例部署时靠 Redis 发布订阅已天然支持，但粘性会话/断线补发
  需要引入消息序号或改用 SSE + Last-Event-ID。
- **文件存本地卷**：生产应换对象存储（MinIO/S3），上传接口已按可替换设计（filepath 抽象）。
