## 高频面试问题与回答思路

### AI 应用方向

**Q: Agent 和 RAG 管道有什么区别？你为什么两个都做？（v3 后必问）**
RAG 管道是代码写死的固定流程：改写→检索一次→生成，快而便宜，覆盖 80% 的简单问题。Agent 把决策交给模型：通过 Function Calling 给它检索工具，它自主决定检索几次、换什么关键词——"对比 A 和 B"这类多跳问题需要分别检索 A 和 B，固定管道一次检索覆盖不全。代价是多轮 LLM 调用（延迟和成本翻几倍），所以两种模式并存让用户选。护栏：步数上限防死循环，工具全部只读。

**Q: Function Calling 的完整流程说一下？**
把工具的 JSON Schema 随请求传给模型 → 模型返回 tool_calls（函数名+参数）而不是文本 → 后端执行工具，把结果以 role=tool 消息追加回对话 → 再次调用模型 → 循环直到模型不再调工具而是输出答案。要点：参数是模型生成的，必须校验（我这里 json.loads 容错 + 空参检查）；工具执行失败不中断循环，把错误信息返回给模型让它自己调整策略。

**Q: 语义缓存怎么做的？和普通缓存有什么区别？**
普通字符串缓存对"怎么退款"和"退款流程是什么"是两个 key，命中率极低。语义缓存把问题向量化，与缓存条目算余弦相似度，≥0.95 视为同一问题直接返回缓存答案——延迟从秒级到毫秒级、token 零成本。两个关键设计：一致性（知识库文档变更时整体失效该用户缓存，宁可少命中不可答旧数据）、降级（Redis 故障时直接走正常链路）。追问"为什么阈值 0.95"：调低命中率高但可能答非所问，这是准确性和命中率的权衡，可配置可评估。

**Q: 讲一下你的 RAG 流程？**
从两条链路讲：写路径（上传→异步解析→递归切片→bge 向量化→pgvector）和读路径（查询向量化→两路召回→RRF 融合→拼 Prompt→流式生成）。强调"异步"和"混合检索"两个设计点。

**Q: 切片大小为什么选 512？切大切小有什么影响？**
bge-small-zh 有效输入约 512 token，切太长向量表征被稀释、检索变糊；切太短上下文碎片化、LLM 拿不到完整信息。关键是说出：这是可量化调优的参数，我写了评估脚本对比不同取值的 Hit Rate。

**Q: 检索不准怎么优化？（必考）**
分层回答：① 召回层——纯向量对专名不敏感，所以加了关键词召回 + RRF 融合；② 精排层——可开交叉编码器重排（效果↑延迟↑，讲清取舍）；③ 数据层——优化切片策略（段落优先、带重叠）；④ 查询层——bge 查询指令前缀；进一步可做查询改写/HyDE。⑤ 兜底——评估脚本量化每次改动，不靠感觉调参。

**Q: 怎么减少幻觉？**
① System Prompt 强约束"只根据参考资料回答，不足时明说"；② 回答带 [1][2] 编号引用，可溯源；③ temperature 调低（0.3）；④ 检索质量本身是幻觉的上游，检索准了幻觉自然少。

**Q: 为什么用 pgvector 不用 Milvus？**
规模匹配 + 少运维一个组件 + 外键级联保证向量和文档一致性；说明知道什么规模该迁移（千万级向量、需要 GPU 检索/分布式时）。

### Python 后端方向

**Q: 关键词检索为什么不用 LIKE？你的全文检索怎么做的中文支持？（v4 核心故事）**
LIKE '%kw%' 前导通配符无法走 B-tree 索引，必然全表扫描，切片十万级后就是慢查询。升级方案：PostgreSQL 全文检索——但 PG 自带解析器不支持中文分词，所以入库时先用 jieba 分词、空格连接，再交给 to_tsvector('simple')，等于把分词做在应用层、倒排索引交给数据库；配 GIN 索引，查询用 to_tsquery（OR 连接关键词）+ ts_rank 排序。细节加分点：tsquery 有语法字符（& | ! 括号），关键词必须白名单过滤防注入；存量数据用 Alembic 迁移加列 + 回填脚本。追问"为什么不用 ES"：单机规模 PG 够用且少一个组件，检索层已抽象、后续可平滑替换。

**Q: 多轮对话越聊越长，上下文怎么管理？（AI 岗新热点）**
三层设计：① 最近 6 轮原文进 Prompt（细节保真）；② 更早的轮次滚动压缩成摘要（超过 12 条消息触发，旧摘要+新增轮次增量合并，记录覆盖位置避免重复压缩）；③ Redis 只缓存最近轮次。效果：token 成本封顶，20 轮前用户说过的关键偏好也不丢。摘要失败静默跳过——它是增强不是依赖。

**Q: 熔断器是什么？和重试有什么区别？（可靠性必问）**
重试解决偶发抖动，但下游真挂了还拼命重试等于雪上加霜——每个请求都白等一个超时周期，线程/连接被占满，故障从 LLM 扩散到整个服务。熔断器统计连续失败次数，超阈值后直接快速失败（不再发起调用），冷却期过后放行试探（半开），成功则闭合。我的实现是进程级状态（多实例各自熔断，这正是想要的隔离粒度）。再往深聊：改写、追问、语义缓存这些增强功能全部 try/except 静默降级——LLM 全挂时核心接口 P95 不受影响。

**Q: 排查线上问题你有什么手段？**
三层：① 全链路请求 ID——中间件生成 rid 放进 contextvar，该请求所有日志自动带 rid，响应头回传 X-Request-ID，用户报障时拿 ID 一查到底；② Prometheus 指标——HTTP/检索/LLM 首字延迟直方图，看 P95 趋势定位慢在哪一层；③ 业务级用量记录——每次问答的 token 和延迟落库，可按用户/按天核算成本。

**Q: 大文件上传怎么不阻塞接口？**
两层：① 上传本身流式落盘（1MB 一块边读边写边计数，超限即断）；② 耗时的解析/向量化丢给 Celery，接口 202 立即返回，前端轮询状态。加分点：任务幂等（先删旧切片）、失败重试、acks_late 防任务丢失。

**Q: 异步（async）和 Celery 任务队列有什么区别，为什么两个都用？**
async 解决的是 IO 等待期间释放事件循环（高并发连接），Celery 解决的是**长耗时/CPU 密集任务移出请求进程**。向量化是 CPU 密集，放 async 里会卡死事件循环，必须进队列；API 里少量 CPU 操作（查询向量化）用 `asyncio.to_thread` 丢线程池。

**Q: Redis 在项目里做了什么？挂了怎么办？**
三个角色：Celery broker、对话历史缓存（Cache-Aside）、（可扩展）限流存储。缓存操作全部 try/except 包裹，Redis 挂了自动降级直查 PostgreSQL，主流程不受影响——能讲"降级"这个词很加分。

**Q: JWT 和 Session 的区别？JWT 怎么做登出？（必考）**
JWT 无状态、服务端不存储、天然适合水平扩展；缺点是无法主动吊销。本项目的完整答案：双 Token——Access 30 分钟纯无状态（性能），Refresh 7 天存 Redis 白名单（可吊销），登出=删白名单 key；轮换用 GETDEL 原子取删，旧 Refresh Token 用过即废（防重放）；token 带 type 字段防"拿 Refresh 冒充 Access"的类型混淆。再补充：bcrypt 加盐、登录错误信息模糊化防撞库、越权返回 404、按用户隔离数据。

**Q: WebSocket 和 SSE 怎么选？你的通知为什么走 Redis 发布订阅？**
回答流式输出用 SSE（单向、HTTP 语义、断线自动重连简单）；文档状态通知用 WebSocket（演示双向长连接能力）。关键点：Celery worker 和 API 是独立进程，worker 不知道用户连在哪个 API 实例上，所以 worker 只管 publish 到 Redis 频道，哪个实例持有该用户的连接哪个实例就转发——天然支持多实例，无需改造。

**Q: 多轮对话里检索为什么会失效？怎么解决？**
用户第二轮问"那第二条呢"，这句话本身没有任何可检索的语义。解法是查询改写：把最近几轮历史 + 新问题交给 LLM 改写成独立完整问题（temperature=0，限 120 token，失败兜底用原问题），用改写结果检索、用原问题生成。前端把改写结果展示出来，可解释、可调试。

**Q: 数据库设计讲一下？向量字段怎么建索引？**
五张表（users/documents/chunks/conversations/messages），级联删除保证一致性；chunks 冗余 owner_id 避免检索时 join。向量索引用 HNSW（近似最近邻，牺牲一点召回换查询速度），对比 IVFFlat：HNSW 查询快、不用先有数据再建索引，写入稍慢占内存稍多。

**Q: 怎么保证代码质量？**
核心纯逻辑（切片、RRF、JWT）有 pytest 单测；检索效果有独立评估脚本；日志中间件记录每个请求耗时，响应头带 X-Process-Time-Ms 方便排查慢请求。

## 现场演示话术（3 分钟）

1. `docker compose up -d` 起五个容器 → 打开 localhost:8000
2. 注册登录 → 建知识库 → 拖拽上传 PDF → 指着右上角实时弹出的通知讲"Celery 异步处理 + Redis 发布订阅 + WebSocket 推送，不是轮询"
3. 提问 → 流式输出讲 SSE → 展开引用来源讲"PDF 精确到页码，可溯源" → 追问一句带指代的问题，指着"实际检索：xxx"标签讲查询改写
4. 问一个知识库里没有的问题 → 展示模型回答"知识库中没有找到" → 讲幻觉控制
5. 切到用量统计页讲 token 成本核算 → 开 localhost:5555（Flower）讲队列监控 → 开 /metrics 讲 Prometheus 对接
6. 最后打开 /docs 自动接口文档，讲一处你最得意的设计（推荐：GETDEL 防重放或 RRF）

## 提前准备好的"坑"故事（面试官爱听踩坑）

- SSE 用 POST 时前端不能用 EventSource，手写 fetch 流解析，还要处理事件被 TCP 分包截断的情况（buffer 留尾）；
- 流式响应期间请求级 DB session 被回收，落库改用独立 session；
- Windows 上 Celery 默认 prefork 池不可用，要加 `--pool=solo`；
- 国内拉 HuggingFace 模型超时，用 HF_ENDPOINT 镜像解决；
- bcrypt 新版本和 passlib 不兼容，锁定 bcrypt==4.0.1。
